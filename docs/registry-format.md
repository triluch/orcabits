# Registry format

Each `registry/plugins/<id>.yaml` describes one installable OrcaSlicer plugin. IDs use lowercase letters, digits and hyphens and remain stable when a plugin changes its display name. Multiple independently installed plugins may share a repository.

```yaml
name: Example Plugin
summary: Adds an example feature to OrcaSlicer.
description: >-
  Explain the main feature. Explain a second concrete capability.
  Describe the normal workflow. State an important requirement.
  State a verified limitation.
repository: https://github.com/owner/repository
categories:
  - workflow-and-integrations
status: experimental
status_note: Preview release; the author has tested only Windows.
installation:
  method: python
  url: https://github.com/owner/repository#installation
  notes: Install the released Python file through OrcaSlicer's Plugins window.
compatibility:
  orca_slicer: Plugin-enabled OrcaSlicer 2.5 or later.
  platforms:
    - windows
  requires_custom_build: false
  notes: Other operating systems are not verified.
evidence:
  - label: README
    url: https://github.com/owner/repository/blob/main/README.md
updated_at: "2026-11-19"
reviewed_at: "2026-11-19"
```

## Rules

- `summary` is one sentence. `description` is plain text with 4–6 factual sentences, not HTML, a development history or unsupported compatibility guesses.
- `repository` is a public canonical `https://github.com/<owner>/<repo>` URL.
- `categories` contains one or more IDs defined in `registry/catalog.yaml`.
- `status` is `available`, `experimental`, `deprecated` or `archived`; `status_note` explains the evidence behind it.
- `installation.method` is `python`, `wheel`, `source` or `native`. The URL points to an actual artifact or documented install/build instructions, not a scaffold or proposed future workflow. Notes identify the file or companion software when needed.
- `compatibility.orca_slicer` states the documented version/API requirement. `platforms` contains only explicitly supported/tested platforms (`windows`, `macos`, `linux`); use an empty list if unknown. Notes distinguish supported from actually tested platforms.
- `requires_custom_build` is true if stock release/nightly builds cannot run the plugin. Do not confuse ordinary nightly/API version requirements with a custom fork.
- `evidence` contains primary-source URLs supporting functionality, installability and status. Pin source revisions when practical.
- Quote ISO dates. `updated_at` changes when curated plugin information changes; `reviewed_at` changes when sources are checked. Merely reviewing unchanged information must not advance `updated_at`.
- Optional notes may be omitted. Unknown values must not be fabricated.

`registry/github.yaml` is generated by `make update-github`; do not hand-edit star counts. Its `updated_at` changes only when stored repository statistics change. `checked_at` records successful observation and does not advance the displayed data-update date.

## Manual inclusion seeds

`registry/inclusions.yaml` is a maintainer research seed list for specific additions that normal discovery missed and someone explicitly requested. It is not an approval or publication list: research each seed separately and apply the normal installability, evidence, and exclusion rules. Keep the list empty until a specific addition is supplied; do not copy discovered inventory into it.

```yaml
updated_at: "2026-11-19"
inclusions:
  - repository: https://github.com/owner/repository
    plugin_id: optional-stable-id
    note: Requested because ordinary discovery missed this plugin.
    added_at: "2026-11-19"
```

Each entry has a canonical GitHub `repository`, an optional stable `plugin_id` when requesting one plugin from a shared repository, a nonempty `note`, and an ISO `added_at` date. Seeds are unique by repository and optional plugin ID, case-insensitively. A seed cannot conflict with a repository-wide exclusion or a matching plugin-scoped exclusion. Updating this file does not change the displayed data-updated date; only published registry data does.
